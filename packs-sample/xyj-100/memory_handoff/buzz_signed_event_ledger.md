# 出处

`github.com/block/buzz`（Block 公司，Apache 2.0）。2026-07-31 登上 GitHub 周 trending 榜一时发现，当周增长约 1.2 万星。

# 本体

自托管的 Nostr relay。一切动作——消息、表情、工作流步骤、评审批准、git 事件——都是同一条**只追加日志**里的签名事件。人和 agent 共用同一种身份模型：一对 secp256k1 密钥。

技术栈 = Rust（Axum）+ Postgres（事件与全文检索）+ Redis（pubsub）+ MinIO + Tauri。

它**不依赖 git**；git 是被 NIP-34 翻译进总账的「居民」，而不是底座。

# 事件信封六字段

```
{
  id,      // sha256 指纹
  pubkey,  // 身份
  kind,    // 种类编号（整数）
  tags,    // 引用关系
  content,
  sig      // Schnorr 签名
}
```

**`kind` 这个整数是唯一的分拣开关**：新功能 = 新编号 = 零破坏升级。配合哈希链构成防篡改审计日志。

这个信封形状值得单独记住——它把「身份、种类、引用、内容、可验证性」压进了六个字段，任何要做事件流的系统都可以直接对照。

# 它宣称解决的三个病

| 病 | 药方 |
| --- | --- |
| 信息损耗 | 通讯即台账，贴原始线程而非转述 |
| 无效通讯 | 频道成员制 + 签名可归因 |
| 空转 | 事件驱动取代轮询：agent 挂在 relay 上睡觉，事件来了才醒 |

# 引入判据（评估后的结论）

它的重装甲部分——签名身份、防篡改——解决的是「**多支笔互不信任地共同记账**」。如果场景里只有单一写入方，这层成本是纯负担。

而且它只提供总账机制，**不含任何任务语义**（校验门、失败转人工、结论沉淀这些难的部分照样得自己写）。

因此更划算的做法通常是**借鉴信封格式而不搬整套基础设施**：事件格式向它看齐（kind 分拣 + tags 引用 + 哈希链），存储照旧用本地 jsonl。将来真要迁移，只是换个投递地址。

**下列任一条出现，才值得重新评估整体采用：**

1. 出现第二个真正独立的写入主体（另一台机器、另一个人，而不是同一主体的分身）。
2. 需要 agent 常驻的事件驱动形态，且轮询开销真的开始痛。
3. 它的审批门从「胶水未干」的状态转正。
